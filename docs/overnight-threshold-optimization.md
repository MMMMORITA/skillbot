# 阈值与策略参数「过夜优化」方案（以 TTL 提纯感知模型为例）

> 本文脱离代码仓库也能读懂。文中出现的英文符号（如 `val_bpb`、challenger、OOT、maturation window）均在首次出现处随文给中文定义。`train.py` / `prepare.py` / `program.md` 是 Karpathy 开源项目 autoresearch 的三个文件，后文会一一对应到我们的系统。
>
> **业务假设（请按实际情况替换）**：TTL 为业务/场景代号；「提纯感知模型」指一个对请求/用户/流量输出风险分（或低质分）的打分模型，分数本身在优化周期内**冻结不重训**，优化对象是它下游的**决策层参数**——切档阈值、处置阶梯、分层策略与人审抽样。若你的 TTL 模型还包含规则分融合、额度系数等，把它们一并归入下文的参数向量 θ 即可，方法不变。

## 0. 一句话结论

Karpathy 的 autoresearch（自主研究循环器）做的事是：**Agent 改代码 → 训练固定 5 分钟 → 看单一指标是否变好 → 保留或回滚 → 通宵重复约 100 次**。把「训练 5 分钟」换成「在冻结数据切片上回放一次策略」，把「代码」换成「阈值/策略参数」，把「val_bpb（验证集每字节比特数，越低越好的语言模型指标）」换成「固定误杀预算下的坏样本召回」，就得到风控版的过夜优化器：

> **模型不动，每晚自动提出几十上百个阈值/策略假设，在不可变的回放数据上用统一口径裁决，把 Pareto（帕累托，指不存在「不牺牲护栏就更好」的）更优的候选沉淀下来，第二天早上由策略经理 HITL（Human-In-The-Loop，人在环路）审批，再以 challenger（挑战者，灰度对照组）身份小流量上线。**

这是 autoresearch 范式在风控落地成本最低的一条路径：**不碰模型训练、不碰在线系统、纯离线回放 + 灰度门控，且 SkillBot 现有的 Planner/Executor（规划/执行两阶段）、执行回执状态机、HITL 门控、事件台账与快照机制几乎可以原样复用。**

## 1. 为什么优化阈值层，而不是让 Agent 直接改模型

这是方案选型的核心，也是面试必问的「为什么不直接 AutoML 重训模型」。

| 维度 | 重训模型（AutoML 式 autoresearch） | 优化决策层参数（本方案） |
|---|---|---|
| 单次实验成本 | 分钟~小时级，要 GPU、要训练流水线 | 毫秒~秒级，打分已离线预计算，回放只做排序切档 |
| 可回滚性 | 模型权重回滚重，影子观察期长 | 参数是一个 JSON 配置，回滚 = 切回上一版本号 |
| 标签延迟敏感度 | 高：训练标签未成熟会把模型带偏 | 低：可只在「标签已成熟」的切片上回放，标签不够就跳过该切片 |
| 出错爆炸半径 | 全量分数变化，影响所有下游 | 只改决策映射，且可先灰度 1% |
| 可解释/可审计（监管 SR 26-2、EU AI Act 高风险条款要求） | 弱，需要额外 XAI（可解释性）工具 | 强：阈值变更天然可表述为「高于 0.82 拦截」 |
| 夜间可跑实验数 | 十几次 | 数百~上千次 |
| 与提纯场景的匹配 | 提纯的瓶颈往往不是分数排序力（AUC），而是**在业务误杀预算下切点选得好不好** | 正中瓶颈 |

**关键洞察**：感知模型提供的是**排序**（谁比谁更可疑），阈值层决定的是**在排序上切哪一刀、切完怎么处置**。排序能力（AUC/KS，即模型区分度）短期稳定，但「该切在哪」每天都在变——黑产攻击节奏、活动流量结构、误杀预算都在动。模型按周/月迭代，阈值按天迭代，两者周期天然不同。让一个过夜循环去优化慢变量（模型）性价比低，优化快变量（决策层）性价比高。

## 2. 问题形式化（给评审/面试的数学口径）

对每个待决策样本 x（一笔请求、一个用户或一段行为窗口），冻结的感知模型给出分数：

```
s(x) ∈ [0, 1]     # 风险分/低质分，越高越「该被提纯」
```

决策层是一个带参数 θ 的策略函数，把分数（必要时加上人群/渠道等分层键 z(x)）映射为动作：

```
d(x; θ) ∈ {PASS, CHALLENGE, REVIEW, DOWNWEIGHT, BLOCK}
#          放行   弱验证(滑块/人脸) 人审  降权/限流  拦截/清洗
```

θ 至少包含：

- 全局切档点：`[t1, t2, t3]`，例如 `s < t1` 放行、`t1 ≤ s < t2` 弱验证、`t2 ≤ s < t3` 人审抽样、`s ≥ t3` 拦截；
- 分层偏移：按渠道/活动/新老客/设备风险等级 z 对切档点做偏移量 `δ[z]`（高风险渠道切点整体下移）；
- 人审抽样率 r：人审档内按概率 r 送审，受日产能上限 C 约束；
- 处置强度参数：降权系数、冷却时长（多久内重犯直接升级处置）、阶梯计数窗口。

在一个**冻结且标签成熟**的回放切片 D 上，定义：

- **坏样本**（应被提纯对象，标签 y=1）：标签来源见 §4.3，典型为事后封禁确认、设备/团伙聚类命中、套利/套现核实；
- **主指标**：`Recall@FPR≤b` —— 在误杀率（好样本被处置的比例）不超过预算 b 的前提下，坏样本召回率；也常用业务化版本 `坏样本拦截量@日误杀量≤M`；
- **提纯浓度**：处置集合中真实坏样本的占比 `precision`（提纯后「纯度」），这是「提纯」业务最直观的北极星口径；
- **护栏指标**：人审量 ≤ C、弱验证打扰率 ≤ q、核心人群（如新客、高价值用户）误杀 ≤ 分层上限、预估资损/补贴套利金额变化。

优化问题：

```
max_θ  Recall(D; θ)                      # 主目标：多抓到坏人
s.t.   FPR_good(D; θ) ≤ b                # 误杀硬预算
       review_volume(D; θ) ≤ C           # 人审产能硬约束
       guardrail_j(D; θ) ≤ g_j,  ∀j      # 各分层护栏
       θ ∈ Θ_safe                        # 参数只允许在安全域内取值（见 §7.1）
```

输出不是一个单点，而是一条 **Pareto 前沿**（同样召回下误杀更低、或同样误杀下召回更高的若干个 θ），最终选哪个点是**业务取舍**，由人在 HITL 门决定——系统只负责把前沿算准、把证据摆全。

## 3. Karpathy 三要素的逐一对齐

| autoresearch 要素 | 原版含义 | 提纯阈值过夜优化对应物 |
|---|---|---|
| 不可改的 `prepare.py` | 固定数据、tokenizer、评估函数，保证实验仪器一致 | **仪器层**：冻结数据快照、固定 OOT（Out-of-Time，按时间切分，用过去训练/调参、用未来验证）切片、成熟窗、统一标签口径与指标实现 |
| Agent 唯一可改的 `train.py` | GPT 模型/超参/优化器全部可改 | **策略配置 θ**：切档点、分层偏移、抽样率、处置参数（一个受 schema 约束的 JSON，而非任意代码） |
| 固定 5 分钟预算 | 墙钟固定，保证不同改动可公平比较 | **固定回放协议**：同一批样本、同一份预计算分数、同一标签版本；每次评估 O(回放全量) 时间近似常数 |
| 单一指标 `val_bpb` | 与词表大小无关，防止刷指标投机 | **主指标 + 硬护栏**：Recall@误杀预算；护栏不达标实验直接判负，防止「靠误杀换召回」的指标投机 |
| 指标变好就保留提交 | git 式 keep/discard | θ 进入候选池（不自动上线），晨会人审后以 challenger 灰度 |
| 人改 `program.md` 调「研究组织」 | 编排方式由人迭代 | 人维护：参数搜索空间、护栏阈值、坏样本口径、假设模板 |

最大的相同点是**「提案—执行—证据裁决」的闭环全部由机器跑完，人只在两个点介入：事前设边界、事后做审批**。最大的不同点（也必须在答辩时主动讲）：原版无监管、可自动保留；风控版**禁止自动上线**，机器的权力终止于「产出带证据的候选」。

## 4. 仪器层：固定测量口径（最容易做错、最值钱的部分）

Karpathy 用一个不许修改的 `prepare.py` 保证「每 5 分钟实验彼此可比」。风控回放如果口径不锁死，跑 1000 个实验等于生产 1000 份互相不可比的废纸。仪器层由四块构成。

### 4.1 不可变数据快照

- 每晚从数仓切出一份**只读快照**并打内容哈希（content hash，用于证明所有实验用的是同一份数据），路径形如 `snapshots/dt=2026-10-25/data.parquet`；
- 快照内的 `s(x)` 是**预计算并冻结**的模型分（记录模型版本号 `model_revision`），优化过程绝不重算分数——否则「阈值效应」和「分数漂移」混在一起，无法归因；
- 实验台账（§8）必须记录 `data_hash`、`model_revision`、`label_version` 三元组，三者任一变化，旧实验结果一律标记为「不可横比」。

### 4.2 OOT 切分与多个时间窗口

不用随机切分（随机切分在风控上是作弊：同团伙、同设备的样本会横跨训练/验证集造成泄漏）。采用时间切分：

```
|--- 调参搜索窗（search window）---|--- 裁决窗（judge window）---|
        假设在这里提出、初筛              只在这里算正式成绩、定胜负
```

- 搜索窗与裁决窗**时间不重叠**，防止 Agent 过拟合到同一段数据（等价于原版 val 集与 train 的分离）；
- 额外保留多个短窗（如近 1 天 / 3 天 / 7 天）分别出成绩：只在单窗有效的策略标注「窗敏感」，防止吃到某次活动脉冲的伪改进；
- 每月留一次**背靠背 champion-challenger 离线回放**：现网策略（champion，卫冕者）作为一个普通候选一起跑，它的成绩就是「改进量」的零点。

### 4.3 标签成熟度（maturity window）——风控特有的第一道闸门

风控标签不是立等可取的：一笔交易当时放行，可能 30 天后才出现拒付/逾期；一个用户当时没封，可能两周后被团伙聚类确认为刷子。直接用未成熟标签当 y=0 会制造大量**伪好样本**，把阈值往激进方向带偏。

规则：

```
样本事件时间 t_event，标签成熟截止 t_mature = t_event + L
只有 t_event + L ≤ 快照制作日 的样本才允许进入评估切片
```

- L 按业务定（套现确认、设备聚类、人工举报各有不同延迟，取覆盖主要来源的分位，如 P90 标签到达时长）；
- 用**到达函数（label arrival curve）**刻画不同 L 下标签累积比例，写进实验报告，让审批人知道「这批成绩覆盖了百分之多少的坏」；
- 成熟窗内新增标签回流后，**历史实验可复跑复验**（数据和配置都在台账里），发现当初「伪改进」则把候选打回——这是 §9 外循环的重要输入。

### 4.4 选择性标签与拒绝推断偏差（必须写进局限性）

已被现网策略拦截/清洗的人群没有「放行后会怎样」的反事实标签，评估切片天然偏向「被放过的人群」。这叫选择性标签（selective labels）/ 拒绝推断（reject inference）问题。工程上的克制做法：

1. 主口径只在「champion 放行集」上比较候选（这是无偏可比的人群），报告这是**在现有策略边界内的增量改进**；
2. 对「champion 拦截集」只做描述性统计（如分数分布、事后标签浓度），不纳入正式裁决；
3. 真正想评估「切点下移能否抓住边界坏人」，唯一硬证据是**线上定向探测试验**（小流量、短时长、有人审兜底），离线回放只能给假设不能给结论——该结论必须在文档和审批单上写明。

## 5. 参数空间 Θ：Agent 到底能改什么

参数空间要**足够有用但绝不允许任意代码**，用 JSON Schema（带类型与边界的声明式约束）描述，加载即校验，越界直接拒绝实验（fail-closed，失败即关闭原则的沿用）。

```json
{
  "cutoffs":            {"t_challenge": [0.40, 0.90],
                         "t_review":    [0.60, 0.95],
                         "t_block":     [0.75, 0.99]},
  "monotonic":          "t_challenge < t_review < t_block",
  "segment_offsets":    {"channel_risky":  [-0.10, 0.0],
                         "new_user":       [-0.05, 0.05]},
  "review_sample_rate": {"min": 0.0, "max": 1.0},
  "daily_review_cap":   5000,
  "cooldown_days":      {"min": 1, "max": 14},
  "protected_segments": ["vip", "staff"],
  "max_delta_vs_champion": 0.03
}
```

设计要点（都是踩坑口径）：

1. **单调性硬约束**：三个切点必须有序，由生成器保证、由校验器复验；
2. **与 champion 的最大单步位移** `max_delta_vs_champion`：每夜探索是「局部爬山」而不是「随机跳崖」，防止一个离谱配置在离线指标上偶然占优；大改动必须走人工立项；
3. **保护人群硬编码不可动**：VIP、内部员工等分层只能更宽松不能更严，且不从 Agent 的提案里读取（防注入/防幻觉改名单）；
4. **动作枚举封闭**：Agent 不能发明新动作（不能自己提出「封号」这种没在执行系统注册的处置），只能在五个既有动作上调切点；
5. **分层键白名单**：只有数仓里稳定存在、通过缺失率/基数检查的维度才能做 z 分层。

**三类提案生成器（Planner 的实现）**，夜里按配额混合使用：

- **确定性网格/邻域搜索**：以 champion 切点为中心做网格扰动，保底覆盖局部地形（不依赖 LLM，结果可复现）；
- **贝叶斯优化（BO，如高斯过程/TPE）**：以「召回−护栏罚项」为目标做样本高效搜索，适合连续切点；
- **LLM 假设生成器**：喂给它 badcase 聚类摘要、人审翻案记录、漂移报告（只给聚合统计，**不喂用户明细**），让它提出可解释的分层假设（如「某渠道凌晨档分数整体虚高，建议该分层切点上移 0.02」），输出必须是符合 schema 的 θ + 一段假设陈述，假设陈述进台账供人审。LLM 负责「提出有意思的方向」，BO 负责「把数值磨到最优」，网格负责「兜底与地形测绘」。

## 6. 指标契约：什么证据才能让一个候选「赢」

对应原版的单一 `val_bpb`，但风控不可能只看一个数。契约分三层，裁决器按顺序执行：

**第一层：硬门槛（不过直接判负，不看主指标）**

- 裁决窗 FPR ≤ b；人审量 ≤ C；
- 每个保护分层误杀不超各自上限；
- 全部子窗（1/3/7 天）护栏均达标，不允许用均值掩盖单点爆炸；
- 配置通过 schema 与单调性校验。

**第二层：主指标比较（在过门槛的候选里）**

- 主排序键：裁决窗坏样本召回相对 champion 的提升 ΔRecall；
- 要求**统计显著**而非数字更大：坏样本是稀疏正例，提升量要给置信区间（Wilson 区间或自助法 bootstrap），下界 ≤ 0 的候选标记为「不显著」，默认不晋升；
- 在多个人群分层上报告召回/误杀，防止「总量变好、某分层崩塌」。

**第三层：业务价值与 Pareto 归档**

- 把每个过门槛候选算成业务货币口径：多拦坏样本 × 单均损失 − 多误杀 × 单均打扰成本 − 多人审 × 单均审核成本；
- 不强制选货币值最大的（单价本身有争议），而是把 Pareto 前沿上的 3~5 个点全部摆给审批人，附「每个点多抓多少、多杀多少、多审多少」。

**反 Goodhart（古德哈特定律：指标一旦成为目标就会被钻空子）条款**：

- 候选 θ 不许出现在它自己的生成依据里（防止 LLM 对着裁决窗数字反推参数）；搜索窗/裁决窗分离也是为此；
- 任何候选必须**同时**在背靠背的 champion 回放中比较，且报告 `ΔRecall` 而不是绝对值；
- 晋升为 challenger 后，离线成绩不视为结论，线上灰度的实测指标（含延迟标签回流后的复盘）才是终局证据。

## 7. 过夜主循环：完整流程与伪代码

### 7.1 总流程

```
23:00  T-1  仪器层就绪
       拉取冻结快照 → 预计算分数落盘 → 标签成熟度过滤 → 切 search/judge 双窗
       champion 配置与现网 model_revision 登记入台账
  │
  ▼
23:30  Planner（对应 SkillBot 计划阶段，只读）
       输入：champion θ、badcase 聚类摘要、人审翻案摘要、漂移报告（全聚合数据）
       产出：N 个候选假设 {θ_i, rationale_i}（rationale：自然语言理由）
       约束：schema 校验 / 单调性 / 安全域 / max_delta —— 不合法即丢弃并记录
  │
  ▼
00:00  Executor（对应 SkillBot 执行阶段，串行 + 幂等）
       for θ_i in 候选队列（按「网格 → BO 补充 → LLM 假设」优先级）:
         在 search 窗快速评估 → 粗筛掉明显劣化
         通过者在 judge 窗正式评估 → 三层指标契约裁决
         结果追加写实验台账（JSONL 事件流，append-only 只追加不可改）
         失败/超时/NaN：auto-fix（重试上限 3 次）后判负，绝不静默跳过
  │
  ▼
06:00  收敛与报告
       对全部成绩做 Pareto 排序、置信区间、分层明细
       与 champion 逐项对比；对历史已晋升候选触发「标签回流复验」
       生成晨会报告（HTML/飞书文档）：前沿候选 + 证据 + LLM 理由 + 风险标注
  │
  ▼
09:30  HITL 门（人审，系统无自动上线权）
       策略经理：批准灰度 / 要求改护栏 / 拒绝
       批准者 → 注册 challenger 实验：1% 流量、固定时长、人审兜底、一键回滚点
  │
  ▼
T+N    外循环：灰度到期 → 延迟标签成熟 → 复盘 → 晋级 champion 或淘汰
```

### 7.2 伪代码（Python 风格，仅表达逻辑，非实现）

```python
# ============ 仪器层：全局只读，任何实验不得修改 ============
instrument = build_instrument(
    snapshot_date="2026-10-25",
    model_revision="ttl-percept-v17",     # 冻结的感知模型版本
    label_version="lbl-2026-10-25",
    maturity_lag_days=L,                  # 标签成熟窗
)
# instrument 内含：search_window, judge_window, 预计算分数 s(x), 成熟标签 y, 分层键 z
assert content_hash(instrument) in LEDGER   # 哈希入台账，事后可证「同一份仪器」

champion = load_config("policy://champion") # 现网策略 θ
write_ledger(event="instrument_ready", hash=..., model_revision=..., champion=...)

# ============ Planner：提出候选（纯函数，无任何线上副作用）============
candidates = []
candidates += grid_around(champion, step=0.01)          # 1) 邻域网格兜底
candidates += bayes_suggest(instrument.search_window,
                            objective=composite_reward, # 2) 贝叶斯优化
                            budget=80)
candidates += llm_hypotheses(                           # 3) LLM 读聚合诊断提假设
    inputs=[badcase_clusters(), review_overturns(), drift_report()],
    schema=POLICY_SCHEMA,                                #    只能输出受约束 θ
    max_proposals=20,
)

validated = []
for c in candidates:
    if not POLICY_SCHEMA.validate(c.theta):   write_ledger("rejected", c, "schema"); continue
    if not monotonic_cutoffs(c.theta):         write_ledger("rejected", c, "monotonic"); continue
    if not in_safe_region(c.theta, champion):  write_ledger("rejected", c, "safe_region"); continue
    if touches_protected_segment(c.theta):     write_ledger("rejected", c, "protected"); continue
    validated.append(c)                       # fail-closed：任何异常都不放行实验

# ============ Executor：串行、幂等、有终态回执 ============
for attempt in run_batch(validated, idempotency_key="dt=2026-10-25"):
    # 幂等键 = 数据日期 + 配置哈希；重复/乱序/迟到回执按幂等规则丢弃，不重复记账
    try:
        quick = replay(instrument.search_window, attempt.theta)
        if quick.guardrails_fail() or quick.recall <= champion_recall_search:
            write_ledger("eliminated", attempt, quick); continue      # 粗筛

        final = replay(instrument.judge_window, attempt.theta)         # 正式裁决窗
        verdict = judge(final, champion_on_judge, instrument)          # 三层契约
        # judge 内部：硬门槛 → ΔRecall 置信区间下界 > 0 → Pareto/货币化
        write_ledger("evaluated", attempt, final, verdict)
    except (NaNMetric, ReplayError, Timeout) as e:
        ok = autofix(attempt, retries=3)                 # 与 SkillBot auto-fix 同上限
        write_ledger("failed", attempt, error=e, autofixed=ok)

# ============ 收敛：只产出候选，权力终止于此 ============
frontier = pareto_front(read_ledger(date=today, status="evaluated"))
promote_candidates(frontier, report=True)     # 进晨会报告，等待 HITL；不触碰线上
```

### 7.3 auto-fix 与失败语义（沿用 SkillBot 纪律）

- 回放失败常见原因：维度枚举出现新值、分数空值、人审产能字段缺失。auto-fix 只允许三类**无语义副作用**动作：缺失分层回落到 `default` 桶、空分数归入 `PASS` 并计数、重跑；
- 3 次仍失败：判负并在晨会报告置顶（仪器问题比策略问题更需要人知道）；
- 任何 auto-fix 动作都进台账，审批人可见——**失败和修复过程本身是审计证据，不是内部琐事**。

## 8. 实验台账（事件流 + 快照，直接复用 SkillBot 持久化模式）

台账是「状态外置、可恢复、可审计」原则的落地，也是监管语境下最能打的资产。采用 append-only JSONL（只追加的每行一条 JSON 的事件日志），核心事件类型：

```jsonl
{"event":"instrument_ready","ts":"...","data_hash":"sha256:...","model_revision":"ttl-percept-v17","label_version":"lbl-..."}
{"event":"proposed","hyp_id":"H017","source":"llm","theta":{...},"rationale":"渠道X凌晨档分数虚高..."}
{"event":"rejected","hyp_id":"H018","reason":"safe_region"}
{"event":"evaluated","hyp_id":"H017","judge":{"recall":0.912,"fpr":0.0041,"delta_recall":0.0063,"ci":[0.0021,0.0104],"review_vol":4310},"guardrails":"pass"}
{"event":"promoted_for_review","hyp_id":"H017","pareto_rank":2}
{"event":"human_decision","hyp_id":"H017","decision":"approve_challenger","reviewer":"zhangsan","note":"..."}
{"event":"challenger_started","hyp_id":"H017","traffic_pct":1,"batch_id":"ch-20261027-01","kernel":"policy-engine"}
{"event":"challenger_result","batch_id":"ch-20261027-01","online_metrics":{...},"mature_label_followup":"pending|confirmed|overturned"}
```

设计约定（与 SkillBot 现有机制逐条对齐）：

- **幂等身份三元组**：每条实验记录携带 `protocol_version=1`、`request_id`（单实验唯一）、`batch_id`（夜间批次），复用 Comm v1 的身份约束思想——灰度执行系统无法确定策略版本/流量身份时必须显式失败，禁止静默落到「当前线上配置」；
- **终态语义**：实验/灰度状态 `received → materialized（配置已物化到策略引擎）→ started → succeeded/failed`，异常终态 `rejected/cancelled`，本地超时 `timed_out` 由协调器生成而非执行端返回；
- **环形快照**：每晚的仪器切片 + champion 配置保留最近 50 版（对应现有 MAX_SNAPSHOTS=50），任何历史实验可按 `data_hash + θ hash` 复跑；
- **恢复边界**：快照恢复只覆盖「数据与配置」，不回滚线上策略引擎的外部副作用——线上回滚靠策略引擎自身的版本切换，二者不混淆。

## 9. 外循环：让系统会「换方向」而不只是「磨参数」

内循环（§7）在固定地形上爬山；外循环回答「地形变没变、要不要换山」。这是 autoresearch 双循环架构里「新颖性产生在外循环」的风控版，触发信号有三类：

1. **漂移检测**：分数分布 PSI（群体稳定性指标，衡量两期分布差异）、坏样本率分窗变化、切点附近样本密度变化超阈 → 生成「重新标定」类假设；
2. **badcase 与翻案聚类**：对 champion 漏放（y=1 但 s<t_block）和人审翻案（系统杀了、人放了）做聚类，LLM 读聚类摘要提**新分层/新处置阶梯**假设（注意：提出新分层键仍须通过 §5 的白名单与基数检查）；
3. **标签回流复验**：成熟标签到达后复跑历史 challenger 的成绩，`overturned`（被推翻）次数多的策略族整体降权，对应 SR-Fraud 论文的「结果监督反思 + 记忆演化」——失败经验沉淀为策略知识，喂给下一轮 Planner（SkillBot 的 SkillManager + 失败反哺是现成管道）。

外循环的决策口径是显式三选一，且必须记录理由：

```
CONTINUE   方向有效，继续在该参数区探索（常规夜间爬山）
REVISE     机制成立但参数/分层要改（漂移、护栏擦边）
TERMINATE  连续 K 个周期无显著增益或标签复验翻案 → 封停该方向，释放探索预算
```

## 10. 映射到 SkillBot：要新写什么、复用什么

| autoresearch 部件 | SkillBot 现有资产 | 复用 / 新增 |
|---|---|---|
| Planner 只读生成假设 | `SECTIONS["plan"]` 硬约束（plan 非空、code 必空）、BlockParser 级联解析 | 复用契约机制；新增「策略参数 JSON Schema」与假设模板 |
| Executor 派发 | ExecutionCoordinator：幂等、串行、身份校验、批次、fail-fast、双超时 | 直接复用；执行后端从「IPython 内核」加一个「回放引擎 / 策略引擎」适配器（AbstractBackend 再落一个子类） |
| 执行回执 | Comm v1 五段状态机、重复/乱序/迟到回执幂等处理 | 直接复用语义；`materialized` = 配置在策略引擎生效 |
| HITL 门 | `# %%plan` 面板三档授权（yes / accept_edits / no） | 复用；审批对象从「代码计划」换成「候选策略 + 证据报告」，灰度上线是唯一的 yes 动作 |
| 权限层 | PreToolUse 程序级门控、fail-closed、路径安全规则 | 复用思想；新增「参数安全域校验器」（schema/单调/保护人群/位移上限），不允许只靠 Prompt 约束 LLM 提案 |
| 状态与恢复 | SessionEventRecorder（.run/sessions/ JSONL）、50 版环形快照、四游标增量投喂 | 复用存储模式；台账 schema 见 §8 |
| 知识反哺 | SkillManager、两层 RAG（index 缩域 + manifest 过滤）、TF-IDF | 复用；新增「失败策略族」知识包与漂移周报为检索源 |
| 外循环 | 无（现状只有单轮编排） | **新增**：漂移检测 + 假设注册表 + CONTINUE/REVISE/TERMINATE 决策记录 |
| 多后端 | deer-flow / nanobot / hermes / claude 统一门面 | LLM 假设生成器可挂任意后端；网格与 BO 不走 LLM |

最小落地顺序建议（每步都可独立演示）：

1. **先离线、先无 LLM**：仪器层 + 网格搜索 + 三层指标契约 + 静态晨会报告。这一步不依赖任何 Agent 能力，一晚上就能证明「自动切点比人工切点好多少」，是立项的硬证据；
2. **接 Planner**：LLM 假设生成器接入，对比「网格/BO vs +LLM」的增益（A/B 时不给 LLM 喂裁决窗数字，避免提示引导污染）；
3. **接 Executor 灰度适配器**：打通 challenger 注册与终态回执，先做 1% 有人审兜底的灰度；
4. **接外循环**：漂移信号、标签回流复验、方向台账。

## 11. 风控特有的四条护栏（答辩主动讲，体现生产经验）

1. **延迟标签**：成熟窗外不裁决；所有线上结论以标签回流复盘为准（§4.3）。
2. **成本不对称**：误杀正常用户/商户的代价远高于漏放一笔，护栏是**硬约束不是加权项**；高价值/新客分层单独设限，防止总量指标掩盖群体伤害。
3. **对抗与 Goodhart**：策略明示后黑产会适配，单夜离线提升不代表长期有效；challenger 必须经过跨窗、灰度、延迟标签三重确认；TERMINATE 机制防止在失效方向上空转。
4. **监管可问责**：人对每个上线决策具名负责（台账 `reviewer` 字段）；机器只到「提案 + 证据」；配置全版本可回滚、处置动作集合封闭、保护人群不可被 Agent 修改。这也正好把 SkillBot 的 HITL/fail-closed 立场转化成银行/支付场景的合规优势——对比「fully autonomous、关掉所有权限确认」的原版 autoresearch，我们是**刻意保留闸门**。

## 12. 一页纸面试问答卡

**Q1：这和传统的阈值网格搜索/贝叶斯调参有什么区别？**
A：单看内循环，搜索器确实就是网格+BO，这部分不新。新在三层东西：① LLM 外循环把 badcase 聚类、人审翻案、漂移信号转成**带机制解释的分层假设**，扩大搜索方向而不只是磨数值；② 全流程的证据契约（双窗分离、成熟标签、置信区间、Pareto 归档）让几百次夜跑结果彼此可比、可审计；③ 提案—执行—人审—灰度—标签回流复盘是一个闭环状态机，失败和翻案会反哺下一轮，而不是一张跑完就丢的参数表。

**Q2：怎么证明不是 LLM 在对着指标编参数？**
A：四道隔离：LLM 只收聚合诊断不收裁决窗明细；搜索/裁决窗时间分离；参数安全域与位移上限封死跳崖；最终成绩按置信区间和 champion 增量裁决，且必须经线上灰度与成熟标签复验。离线成绩明确不被当作终局证据。

**Q3：离线回放说策略变好，线上一定变好吗？**
A：不一定，且文档里写明了两个失效源：选择性标签（被 champion 拦的人没有反事实标签）导致只能保证「在现放行边界内」的增量无偏；非平稳对抗导致离线地形过时。所以系统产出物叫 challenger 候选而不是结论，唯一硬证据是带兜底的小流量灰度 + 标签回流复盘。

**Q4：一晚上跑几百个实验，怎么防止凌晨三点的坏配置上线？**
A：坏配置在结构上不可能上线：生成即过 schema/单调/保护人群/位移四重校验；执行层只写离线台账，物理上不连接线上策略写接口；唯一生效路径是次日具名审批 + challenger 1% 灰度 + 人审兜底 + 一键回滚。自主性终止于「证据」，生效权在人。

**Q5：和你的 SkillBot 是什么关系？**
A：SkillBot 是承载层（Harness，自身不含推理，只做感知—组装—推理—解析—派发—回执—状态收敛的编排）；过夜优化是跑在这个 Harness 上的一个垂直工作流。复用的是协议、协调器、状态机、权限层和后端抽象；为风控新写的是仪器层、参数契约、指标裁决器和外循环——边界清晰：现成底座是模型 SDK 与数仓，自研的是编排与可信执行。
