# 运行中操舵 In-Run Steering（脱离仓库可独立阅读版）

> 本文脱离代码仓库也能读懂。出现的英文名（如 `ClaudeSDKClient.query()`、`session_token`、`control_token`、`ExecutionMode`）是代码里的真实符号，保留是为了答辩对齐术语，每个都配了中文解释。「在 xxx.py 中」只表明逻辑位置，正文已把逻辑讲清。

## 一句话结论

用户不必等 Agent 干完当前这一长段任务，就能中途“补一句话”改变它的方向。这条新指令进入的是**同一个正在跑的任务**（同一个 Claude SDK 运行），不排队等繁忙的内核，也不会另开一个并发任务。

## 要解决什么问题

传统交互是“一问一答、答完才能再问”。Agent 一旦开始执行一个长任务（比如“把整个风险知识库都读一遍再总结”），用户只能干等，要么就只能按停止键把整轮推倒重来。这带来两个痛点：

- **等待成本高**：长任务跑到一半才发现方向不对，却只能等它跑完。
- **纠偏成本高**：唯一的干预手段是“停止”，停止等于放弃已经完成的部分，得从头再来。

运行中操舵要做的，就是在**不停止、不重来、不并发**的前提下，把一句新方向塞进正在进行的这一轮里，让模型在“尚未做出的后续决策”上改向。

## 关键边界：操舵能改什么、不能改什么

这一点答辩必须讲清楚，否则容易被追问翻车：

- **能改**：模型**尚未生成**的后续决策。比如让它“别再长篇总结了，只回答某个结论”。
- **不能改**：已经流式显示出来的文本收不回；已经执行完、产生了副作用的工具调用（比如已经写进去的文件）回滚不了。操舵只影响“未来”，不影响“过去”。

实现上，默认**不先调用 `interrupt()`**（打断）。`interrupt()` 只保留给用户显式点“停止”时用。也就是说，操舵是“温和地追加输入”，不是“粗暴地打断”。

## 底层能力：为什么能做到“不重来”

关键在于 Claude 官方 SDK 的客户端对象 `ClaudeSDKClient` 提供了**动态输入**能力——它的 `query()` 方法（发起/追加一次查询）允许在一个已经开始的运行里**继续投喂新的用户输入**。SkillBot 正是复用了这个能力：第二条消息不是新建一个 Client、新建一个任务，而是对**同一个 Client** 再调一次 `query()`，把新方向作为增量输入送进去。模型于是在同一个上下文里、同一个运行里消化这条新指令。

## 通信路径（三段式，配步骤流）

### 第一段：首轮请求照常从内核发起

用户在 JupyterLab 的 Agent Panel（右侧对话面板）里发第一条消息时，走的还是常规链路：

```text
Panel 面板
  → kernel.requestExecute(_panel_input)   # 面板把输入交给 Notebook 内核执行
  → AgentMagic._stream_with_interrupt      # 内核里的中枢方法，发起可被打断的流式请求
  → Claude 服务的 HTTP 接口 /chat/trace   # 真正调用模型、拿到带追踪信息的流式回复
```

用中文说：面板把第一句话交给 Notebook 内核，内核里的中枢逻辑（在 `magic.py` 中）发起一次“可被打断的流式请求”，最终打到本地 Claude 服务的 `/chat/trace` 接口（带执行追踪的对话接口）。

### 第二段：运行一开始，内核先给面板发一个“操舵目标”

运行真正开始前，内核会通过 Comm（Jupyter 内核与前端之间的双向消息通道，全称 Comm，可理解为“内核↔前端的专用消息管道”）向面板投递一次**控制目标**：

```text
AgentMagic
  → Comm 动作 steer_target
  → 负载 {url, run_id, control_token}
```

含义是：内核告诉面板“如果你等下想中途改向，就往这个 `url`（操舵接口地址）发；这一轮的运行编号是 `run_id`；凭据是 `control_token`（控制令牌）”。这三样东西是后面第三段能走通的前提。

### 第三段：内核繁忙时，第二条消息改走独立 HTTP 通道

当内核处于 busy（繁忙，正在跑上一条）状态时，用户再发的普通消息**不再进入内核的执行队列**（否则就得排队等内核空闲），而是由面板前端直接发一条独立的 HTTP 请求：

```text
Panel 面板
  → POST /sessions/{sid}/runs/{run_id}/steer   # 向“某会话的某次运行”提交一条操舵
  → Session.steer()                            # 服务端会话对象处理这条操舵
  → ClaudeSDKClient.query()                    # 对同一个 SDK 客户端追加动态输入
```

**这条请求的关键特性**：它**不去抢当前 SSE**（Server-Sent Events，服务器向浏览器持续推送的长连接，这里指首轮流式回复占用的那条连接）的会话锁，也**不依赖内核去处理一个新的执行请求**。所以哪怕内核正忙得不可开交，这条操舵照样能送达模型。前端“繁忙内核期间直接发 HTTP 操舵”的逻辑在 `panel.ts`（面板前端）里；服务端接收与派发在 `session.py`（服务端会话）里。

## 协议细节（凭据、字段、幂等、限流）

### 两级凭据：session_token 与 control_token

- 创建一个 Claude 会话时，服务端返回一个随机的 **`session_token`（会话令牌）**。只有持有这个令牌的 Notebook 客户端，才被允许调用 `POST /sessions/{sid}/runs`（在该会话下新建一次运行）。它的作用是：**防止一个只知道“会话 ID 可被枚举”的恶意网页**去凭空创建控制通道——光知道 `sid`（会话 ID）没用，还得有令牌。
- 每次新建运行会返回一个随机的 **`control_token`（控制令牌）**。它把后续的每条操舵**限定到某一次具体运行**——你只能操舵你拿到令牌的那一轮，不能拿旧令牌去操舵别的运行。

新建运行的返回体形如：

```json
{
  "run_id": "random-run-id",
  "control_token": "random-control-token"
}
```

### 操舵请求体

```json
{
  "message_id": "client-generated-id",
  "message": "new direction",
  "control_token": "random-control-token"
}
```

- **`message_id`（消息 ID）**：由客户端生成，在**同一次运行内保证幂等**——同一个 `message_id` 重复提交，服务端只当一条处理，避免网络重试导致同一句方向被投喂两次。必须非空，且长度不超过 200 字符。
- **`message`（消息正文）**：新方向文本，单条最多 8000 字符。
- **`control_token`**：见上，用来证明“我有权操舵这一轮”。
- **请求模型禁止携带额外字段**，因此**不能夹带 `execution_mode`（执行模式）**——这是权限设计上的硬约束，见下一节。

### 两段回执：accepted → applied

服务端为每条被接受的操舵分配一个**单调递增的序号 `seq`**（保证顺序、不重号），并**立即返回 `accepted`（已接受）**。等到模型把这一轮真正跑完、产出最终的结束消息 `ResultMessage`（SDK 表示“本次运行结果已出”的消息类型）之后，再通过 trace（执行追踪流）回传 `applied`（已应用）。也就是说，用户会先看到“已排队”，再看到“已生效”。回执如何随 trace 转发，逻辑在 Notebook 侧的 `session.py`（Agent 会话）里。

### 限流与边界条件

- 单条消息最多 **8000 字符**。
- 每次运行最多 **10 条**操舵（防止无限追加把上下文撑爆）。
- `message_id` 必须非空且 ≤ 200 字符。
- **运行进入 `closing`（收尾中）状态后，拒绝新消息**。这是为了避免出现“消息被接受了、但已经没人来消费它”的悬空状态——模型都要收尾了，再塞进来的方向没机会被读取。
- **运行异常结束时**，那些“已接受但还没确认被消费”的消息会被标记为 **`not_consumed`（未消费）**，如实告诉用户“这条没能真正生效”，而不是假装成功。

运行状态机、动态 `query()` 投递、幂等、限流、`closing` 边界这些核心逻辑都在服务端会话 `session.py` 里；对外的“准备运行 / 操舵”两个 API 及令牌校验在 `app.py`（HTTP 服务入口）里；`session_token` 的缓存与运行准备在 `claude.py`（Claude 客户端适配器）里。

## 权限边界（操舵不能提权）

这是设计上最要紧的一条纪律：**操舵完全继承“运行创建时”的 `ExecutionMode`（执行模式）和 `ToolPolicy`（工具权限策略），不能改变授权。**

- 举例：一个 `plan`（仅计划）模式下创建的运行，收到操舵后，**依然不能** Write/Edit 写改文件、也不能自动执行 Cell（代码单元格）。操舵只能改“做什么方向”，不能改“被允许做到什么程度”。
- 正因如此，操舵请求体**在协议层就禁止携带 `execution_mode`**——从源头堵死“借操舵之名偷偷升级权限”的路径。

### 传输层的收口

- HTTP 服务只接受由 **loopback（回环地址，即 `127.0.0.1`，仅本机可访问）** 面板生成的目标 URL，形如 `http://127.0.0.1:9000/...`。面板会**拒绝其他协议、其他主机、其他端口**的目标，防止被诱导把控制通道指向外部。
- 结合前面的两级令牌：`session_token` 挡住“枚举会话 ID 建通道”，`control_token` 把操舵锁死到单次运行。
- 定位：这仍是**可信本机环境下的应用级控制**，服务**不应暴露到公网**。它不是操作系统沙箱，也不防真正的本地恶意提权。

## 用户看到什么（反馈可见、不静默）

面板会给出明确的可见反馈，绝不静默吞掉：

- HTTP 请求成功后显示：`direction queued #<seq>`（方向已排队，带序号）。
- 最终 trace 确认后显示：`direction applied #<seq>`（方向已应用）。
- HTTP 被拒、网络错误、或目标非法时，直接显示 `Direction not delivered`（方向未送达）——让用户立刻知道这次没成功，而不是以为改了其实没改。

这套“排队→应用”的两段反馈，正好对应上文协议里的 `accepted → applied` 两段回执。

## 怎么验证的

### 自动化测试覆盖点

- 运行准备与令牌鉴权（没有正确令牌进不来）。
- SDK 动态 `query()` 投递确实把新输入送进了同一个运行。
- `message_id` 幂等（重复提交只算一条）。
- 空消息、超长消息、非法 ID 都被正确拒绝。
- 每次运行 10 条上限生效。
- 结果消息与 `closing` 收尾之间的竞态（边界时刻的先后顺序）被正确处理。
- 异常运行里“已接受未消费”消息被标为 `not_consumed`。
- 操舵**不能传递或修改** `execution_mode`。
- 当前运行的权限对象在操舵前后**保持不变**。

### 真实 JupyterLab UI 验收（端到端跑通）

1. 在 Agent Panel 发起一个长任务：读取全部风险知识库文档并做总结。
2. 趁内核 busy（繁忙）时，发送第二条消息：“停止长篇总结，只回答 `UI_STEERING_OK`”。
3. 浏览器据此直接向**同一次运行**的 `/steer` 接口发出操舵请求。
4. Claude 的最终响应里确实包含了 `UI_STEERING_OK`（证明新方向被消化）。
5. 面板显示 `direction applied #1`（第一条方向已应用）。
6. 运行完成后，控制目标关闭，**不再接受迟到的操舵**（验证了 `closing` 边界）。

同时，服务端日志确认了这一整条链路：会话创建、运行准备、CORS（跨域）预检、操舵返回 `200 accepted`（已接受）、以及**同一个 SDK 客户端**后续继续产生的工具事件——最后这点尤其关键，它证明新输入进的是同一个运行，而不是另起炉灶。

## 各模块分工（逻辑位置速查）

以下只标逻辑落点，前文已把每处的职责讲清，脱离仓库也能对上号：

- **服务端会话 `session.py`**：运行状态、动态 `query()` 投递、幂等、限流、`closing` 收尾边界——操舵的“大脑”都在这。
- **HTTP 服务入口 `app.py`**：`prepare`（准备运行）/ `steer`（操舵）两个 API，以及令牌校验。
- **Claude 客户端适配器 `claude.py`**：`session_token` 的缓存与运行准备。
- **Notebook 侧 Agent 会话 `session.py`**：把操舵回执随 trace 转发给前端。
- **Notebook 中枢 `magic.py`**：`steer_target`（下发操舵目标）、`steer_receipt`（回执）、`steer_closed`（通道关闭）这几个 Comm 动作。
- **面板前端 `panel.ts`**：内核繁忙期间，直接发 HTTP 操舵的逻辑。
