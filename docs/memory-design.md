# SkillBot Memory 记忆系统设计（脱离仓库可独立阅读版）

> 本文脱离代码仓库也能读懂。出现的英文名（如 `Namespace.delta`、`conversation_store`、`track_cell`、`_seen`）是代码里的真实符号，保留是为了答辩对齐术语，每个都配了中文解释。「在 xxx.py 中」只表明逻辑位置，正文已把逻辑讲清。文中的目录路径、截断上限、版本数是代码里的真实常量，用来精确说明"记住多少、记多久"。

## 1. 一句话结论：Memory 不是一层，是三层各司其职

SkillBot 的"记忆"不是单一的对话历史，而是**三套彼此独立、职责不同的存储**，分别回答三个不同的问题：

| 层 | 名字 | 回答的问题 | 存在哪 | 谁来读 |
|---|---|---|---|---|
| 第一层 | 会话记忆（对话历史） | "我们之前聊了什么" | 浏览器 localStorage + 磁盘镜像 `.run/conversations/` | 用户（UI 恢复）+ 面板切换器 |
| 第二层 | 运行时上下文（Namespace） | "Notebook 现在是什么状态" | 内核进程内存 | 模型（每轮喂给它） |
| 第三层 | 快照（版本历史） | "某个单元格/整个 Notebook 的历史版本长什么样" | 磁盘 `.run/cell_snapshots/`、`.run/notebook_snapshots/` | 用户（恢复复盘） |

**为什么要拆三层**：这三种记忆的**生命周期、消费者、容量策略完全不同**。对话历史要跨浏览器/跨重启存活、给人看；运行时上下文要低延迟、增量喂给模型、随内核走；快照要能回滚、按版本留存。硬塞进一层会互相拖累——所以拆开。答辩时这是核心论点：**Memory 的设计难点不在"存什么"，而在"用三种不同的存储策略匹配三种不同的记忆需求"。**

## 2. 第一层：会话记忆（对话历史的磁盘镜像）

### 2.1 解决什么问题

Agent Panel（右侧对话面板）里的每一轮问答、渲染出的 HTML、当前模式和状态，前端本来是存在浏览器的 localStorage（浏览器本地存储，快但只属于当前这台浏览器）里的。问题是：**换一台机器、换一个浏览器、或者 JupyterLab 重启，这些对话就没了。** 而且面板需要一个"会话切换器"，能列出"我在哪些 Notebook 上跟 Agent 聊过"。

### 2.2 怎么做的（在 `conversation_store.py` 中）

做法是**把前端的对话缓冲镜像一份到磁盘**，作为 localStorage 的持久化后备：

- **按 Notebook 隔离**：每个 Notebook 对应一个独立的对话文件。文件名用 `md5(notebook_path)[:12]`——即把 Notebook 完整路径做 MD5 哈希后取前 12 位十六进制字符。这样同一个 Notebook 永远映射到同一个文件，且文件名不暴露真实路径。这个哈希方案和快照层是**同一套**（`snapshot_utils`），保证一致。
- **原样存储**：前端已经把对话序列化成一个 JSON 字符串（含输出 HTML、历史、模式、状态），后端**逐字**（verbatim）存下来，再额外记一个 `path`（原始路径）字段——这样切换器恢复时能给会话打上可读的标签。存储结构就是 `{"path": 原始路径, "buffer": 前端的JSON串}`。
- **四个操作**：保存（`save_conversation`）、加载（`load_conversation`，返回缓冲串或空串）、列举（`list_conversations`，扫描目录返回所有 `{path, key}` 供切换器用）、删除（`delete_conversation`，用户从切换器移除会话、或底层 `.ipynb` 文件被删时调用）。
- **失败不炸**：所有操作都包在 try/except 里，出错只记 debug 日志、返回失败值（False 或空串），**绝不让"存历史失败"影响主流程**——记忆是增强项，不是关键路径。

### 2.3 一个关键约束：切 Notebook 要重置 LLM 记忆

后端的 `AgentMagic`（调度中枢）是**内核级单例**，只持有**一个** LLM 会话。所以当用户切换或打开另一个 Notebook 时，必须**重置 Agent 的对话记忆**（在 `magic.py` 的 Notebook 切换处理里），否则新 Notebook 会继承上一个 Notebook 的聊天历史，造成串扰。

**但要划清边界**：这里重置的**只是 LLM 记忆**（模型上下文里的对话）。内核的 Python 命名空间（变量、导入的库）是**整个内核共享**的，同一个内核上的所有 Notebook 用的是同一份 Python 环境，**做不到按 Notebook 隔离**。这是答辩防守点——不能宣称"完全隔离"。

## 3. 第二层：运行时上下文（Namespace 增量投喂）

### 3.1 解决什么问题

模型要在 Notebook 里干活，就得"看见"现场：现在有哪些变量（`df` 是什么形状）、最近几格代码跑了什么、输出和报错是什么、用户改了哪些还没跑的单元格。但如果**每一轮都把整个现场全量重发**给模型，token 成本会随对话变长而爆炸。所以核心诉求是：**既要让模型看见现场，又要尽量少重复发已经发过的东西。**

### 3.2 核心机制：全量快照 vs 增量投喂（在 `namespace.py` 中）

`Namespace`（命名空间抽象，包裹 IPython 的 `user_ns` 用户命名空间）提供两个方法，对应两种投喂策略：

- **`context()` 全量快照**：把当前所有用户变量 + 最近单元格 + 待执行编辑一次性组装成文本。用在"新会话开场"这种需要交代完整现场的时刻。
- **`delta()` 增量**：只返回"上次投喂之后新增的部分"——新变量、新单元格、新的待执行编辑、新的钩子事件。如果什么新东西都没有，直接返回空串。这是**每轮对话的默认投喂方式**，是省 token 的关键。

### 3.3 增量怎么做到的：四个游标

`delta()` 的"增量"靠**四个游标（cursor，记录"上次读到哪了"的下标/集合）**实现，每次投喂后游标前移，下次只取游标之后的新内容：

| 游标 | 追踪什么 | 类型 |
|---|---|---|
| `_seen` | 已经喂过的变量名集合 | 集合（比对新变量用） |
| `_cell_idx` | 单元格列表已喂到的下标 | 整数下标 |
| `_pending_idx` | 待执行编辑已喂到的下标 | 整数下标 |
| `_hook_idx` | 钩子事件已喂到的下标 | 整数下标 |

`delta()` 的逻辑流：① 取当前所有变量，减去 `_seen` 得到"新变量"，再把新变量并入 `_seen`；② 取 `_cell_idx` 之后的新单元格，游标推到末尾；③ 待执行编辑、钩子事件同理；④ 四类都空则返回空串，否则组装成文本。`reset()` 会把四个游标全部清零——用在会话重置时。

### 3.4 记什么、记多少（截断策略）

为了控制 token，各类记忆都有**明确的截断上限**，这些是代码里的真实常量：

- **单元格执行 `track_cell`**：代码截断到 1500 字符，输出和错误各截到 500 字符。
- **待执行编辑 `track_pending_edit`**：用户改了但还没运行的单元格源码，截到 3000 字符。
- **组装成文本时（`_build_context`）**：最近单元格只取**最后 5 个**、待执行编辑只取**最后 3 个**、钩子事件只取**最后 10 个**；且在文本里进一步压缩——单元格代码只显示前 200 字符、输出前 150、错误前 150。
- **变量描述 `_describe`**：不是把变量值全序列化，而是**智能摘要**——DataFrame 显示形状和前 3 行预览、Series 显示长度和前 3 项、list/dict 显示长度和前 5 个元素、字符串超过 80 字符就截断加省略号。这样模型能"认识"变量而不必吞下全部数据。

### 3.5 几种写入入口

除了自动追踪单元格执行（`track_cell`），Namespace 还提供几个主动写入口：`track_pending_edit`（前端记录未执行的编辑）、`remove_cell`/`remove_cell_by_id`（Notebook 里删了单元格时同步移除跟踪，后者用于单元格优化后）、`track_context`（往上下文里插一条"系统备注"，标记为 `context_note` 类型，在文本里显示成 `[system] ...`）、`track_hook`（记录钩子活动事件，在文本里汇总成 `## Hook Activity` 段）。还有 `inject`（往命名空间注入变量，重名会警告并覆盖）和 `remove`（删变量，但保护 IPython 内部变量不被删）。

## 4. 第三层：快照（版本历史与回滚）

### 4.1 解决什么问题

前两层是"给模型看的上下文"，会滚动截断。但用户有时需要**回到某个历史版本**——"这个单元格我改坏了，想恢复到上一版"，或"整个 Notebook 半小时前是什么样"。这需要**不被截断的、按版本留存的持久化快照**。

### 4.2 单元格级快照（在 `cell_snapshot.py` 中）

- **触发**：每次单元格执行时自动保存一版。
- **存储路径**：`.run/cell_snapshots/<notebook>/<cell_id>/vNNNN.json`，其中 `<notebook>` 用和会话层同一套哈希隔离，`vNNNN` 是四位版本号（如 `v0042`）。
- **环形缓冲（ring buffer）**：每个单元格最多留 `MAX_VERSIONS=50` 版。到上限时**删最老的一版**，再写新版——保证磁盘不无限增长，同时留足够的回溯深度。
- **存的内容**：`cell_id`、时间戳、完整代码（**不截断**，这是和运行时上下文的关键区别）、输出（截到 5000 字符）、错误（截到 2000 字符）。
- **对外能力**：`list_versions`（列某单元格所有版本，最新在前）、`get_version`（取指定版本）、`restore`（返回某版本的代码用于恢复）。

### 4.3 Notebook 级快照（在 `notebook_snapshot.py` 中）

- **触发**：在某个时间点捕获**整个 Notebook 所有单元格**的内容和输出。
- **存储路径**：`.run/notebook_snapshots/<notebook>/<timestamp>.json`，用时间戳命名。
- **容量**：最多留 `MAX_SNAPSHOTS=50` 个，超了从最老的开始 `_prune`（修剪）。
- **数据来源**：可以传入单元格列表，也可以从 `AgentMagic` 单例的 `Namespace._cells`（已跟踪的单元格）自动取。
- **对外能力**：`list_snapshots_for`（列某 Notebook 的快照，带前 5 个单元格首行预览和单元格总数）、`get_snapshot`、`restore`（返回快照里的全部单元格）。

### 4.4 快照恢复的权限约束

快照恢复要受权限层约束（见权限文档）：**只在空闲态允许恢复**，恢复时临时授予 `edit`（仅编辑）权限，派发完立刻撤权，且**不自动运行**恢复后的单元格——避免"恢复"意外触发执行副作用。

## 5. 三层如何协同（一轮对话里各层怎么动）

用一轮"用户提问 → Agent 生成并执行代码"串起来看三层的分工：

1. **开场组装**：新会话时，第二层 `Namespace.context()` 给模型一份全量现场（有哪些变量、最近单元格）；同时第一层可能已从磁盘恢复了历史对话，让模型知道"我们之前聊过什么"。
2. **对话进行中**：每轮只用第二层 `delta()` 增量投喂"自上次以来的新变化"，省 token。
3. **代码执行后**：`post_run_cell` 钩子（每格跑完触发）做三件与记忆相关的事——调 `track_cell` 更新第二层运行时上下文、调单元格快照保存第三层版本、（在需要时）触发 Notebook 快照。
4. **对话落盘**：面板把这一轮的对话缓冲同步到第一层磁盘镜像，保证重启不丢。
5. **用户回溯**：用户想回滚时读第三层快照；想切到别的 Notebook 会话时，第一层切换器列出候选、加载对应磁盘镜像，同时 LLM 记忆被重置。

**关键分工纪律**（呼应 harness 的"执行结果与输出采集分离"原则）：`post_run_cell` 只负责**采集记忆**（更新上下文、拍快照），**不碰工作流状态**——状态由回执驱动的状态机管。记忆系统是"旁路"，坏了不影响主执行闭环。

## 6. 设计权衡与边界（答辩防守）

- **为什么增量投喂而不是全量？** 全量会让 token 随对话长度线性膨胀；四游标增量把"重复发送"降到最低，只在开场付一次全量代价。
- **为什么运行时上下文要截断，快照却不截？** 两者消费者不同：运行时上下文喂模型、要控 token，所以激进截断（变量只摘要、单元格只留最近 5 个）；快照给人回滚看、要保真，所以代码不截断、留 50 版。
- **为什么会话历史用哈希文件名？** 既做到"同一 Notebook 稳定映射同一文件"，又不在文件名里暴露真实路径。
- **隔离边界要说清**：切 Notebook 只重置 **LLM 记忆**；**Python 内核命名空间是全内核共享的，无法按 Notebook 隔离**——这是单内核单例架构的固有约束，不能夸大成"完全隔离"。
- **记忆是增强不是关键路径**：三层的所有磁盘操作都容错，失败只记日志，不阻断主流程。
- **不是无限记忆**：会话历史随浏览器/磁盘留存，但运行时上下文会滚动截断、快照是 50 版环形缓冲——都不是"永久全量记忆"，答辩要如实说。

## 7. 目录与常量速查

```text
.run/conversations/<md5(path)[:12]>.json          # 第一层：对话磁盘镜像
.run/cell_snapshots/<notebook>/<cell_id>/vNNNN.json # 第三层：单元格版本快照（≤50 版/格）
.run/notebook_snapshots/<notebook>/<timestamp>.json # 第三层：Notebook 整体快照（≤50 个）
```

| 常量 | 值 | 含义 |
|---|---|---|
| 会话文件名哈希 | `md5(path)[:12]` | Notebook 路径 → 稳定文件名 |
| `track_cell` 代码截断 | 1500 字符 | 运行时上下文里单条代码上限 |
| `track_cell` 输出/错误截断 | 各 500 字符 | 运行时上下文里输出/错误上限 |
| `track_pending_edit` 截断 | 3000 字符 | 未执行编辑上限 |
| 组装取最近单元格 | 最后 5 个 | 喂给模型的单元格窗口 |
| 组装取待执行编辑 | 最后 3 个 | 喂给模型的编辑窗口 |
| 组装取钩子事件 | 最后 10 个 | 喂给模型的钩子事件窗口 |
| `MAX_VERSIONS` | 50 | 单元格快照环形缓冲版本数 |
| `MAX_SNAPSHOTS` | 50 | Notebook 快照留存数 |
| 单元格快照输出/错误 | 5000 / 2000 字符 | 快照里输出/错误上限（代码不截断） |
