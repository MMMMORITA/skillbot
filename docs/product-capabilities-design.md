# SkillBot 产品化能力技术文档（脱离仓库可独立阅读版）

> 覆盖五项支撑能力：会话隔离、Skill 管理、Skill 评测与优化、可观测、恢复与复盘。它们不是三大核心设计（Plan / 知识库 / 操舵），但共同把 Panel 从“聊天窗口”变成“可日常使用的分析工作台”。

## 1. 隔离 Notebook 会话

### 1.1 解决的问题

早期 Agent 会话是**全局单例**、和具体 Notebook 没有绑定。于是出现三个真实故障：
- 打开多个 Notebook 时，对话历史互相串（在 A 里聊的上下文被带到 B）；
- 任务运行中切换 Notebook，切换动作丢失或让面板卡死；
- 切换后仍复用旧内核的通信通道，导致代码发错地方。

### 1.2 隔离的两个维度：对话隔离，但变量共享

这是最容易被追问的点，先讲清边界：

- **对话隔离**：每个 Notebook 有自己独立的 Agent 对话历史，互不串。
- **内核变量共享**：如果两个 Notebook 共用同一个内核，那么 Python 变量（DataFrame 等）仍然是共享的。**隔离的是“对话”，不是“同一内核里的变量”。** 切换时前端会明确提示用户“新 Notebook —— 全新对话，但内核变量跨 Notebook 共享”。

### 1.3 实现（在 magic.py 中）

前端按 Notebook 路径各存一份对话缓冲；后端用几个函数管理会话与 Notebook 的绑定：

- **`_handle_notebook_switch(nb_path)`（处理 Notebook 切换）**：JupyterLab 的“当前 Notebook 变了”事件会触发它。
  - **防抖**：只有当新路径和当前会话绑定的路径**真的不同**时才动作，避免“切标签页、恢复布局”这类假事件误触发重置。
  - **忙时推迟**：如果此刻 Agent 不空闲（状态不是 IDLE），就把目标路径存进 `_pending_session_nb_path`（待切换路径）直接返回，**绝不在任务中途重置会话**。
- **`_apply_pending_notebook_switch()`（补做被推迟的切换）**：任务结束回到空闲时被调用，把刚才缓存的待切换路径真正切过去。如果期间用户切了好几次，只认最后一次（last-path-wins，最后路径优先）。
- **`_switch_notebook_session(nb_path)`（真正执行切换）**：把后端会话绑定到新路径。若和上次相同则跳过；首次绑定或会话还没启动则不用重置。真正切换时，清理旧会话（`cleanup`），并把“会话就绪”标志置为假——下次用户发消息时**懒加载**重建一个干净会话，让新 Notebook 不继承上一个的对话历史。

**换内核的处理**（在前端）：监听“内核已变”事件，先重置通信通道再重新绑定——修“切内核后 Comm 失效”的问题。

### 1.4 与状态机的配合

后端状态机（见主技术文档）有个属性 `should_defer_notebook_switch`（是否该推迟切换，非空闲即为真）判断“现在忙不忙”；回到空闲态时状态机会发出 `APPLY_PENDING_NOTEBOOK_SWITCH`（应用待切换）效果，正好触发 1.3 里的补切逻辑。**“忙时缓存、闲时补切”这套机制由状态机和 magic 协作完成。**

## 2. 管理 Skill

### 2.1 解决的问题

知识/能力接进来后，用户不知道“有哪些 Skill、当前哪些启用、里面装了什么”。需要一个可查、可开关、可安装卸载的管理入口。

### 2.2 核心类 SkillManager（文件 chat/skill.py）

每个后端一个 `SkillManager`（Skill 管理器），管理该后端 Skill 目录下的增删查启停。

**状态持久化**：启停状态存在 Skill 目录下的一个 `.skill_state.json` 文件里，结构是 `{"disabled": [...被禁用的], "enabled": [...被显式启用的]}`。`_load_state` / `_save_state` 负责读写。**用户的显式操作永远优先于默认策略。**

**递归发现 `_discover_skill_mds`**：递归扫描目录找每一个 `SKILL.md`。规则是——一个目录只要直接含 `SKILL.md` 就被当作一个 Skill 的根，**不再往里递归**（Skill 不嵌套 Skill）；跳过隐藏目录（`.git` 等）和 `__pycache__`。这样同时支持两种布局：扁平布局（`目录/技能/SKILL.md`）和分类布局（`目录/分类/技能/SKILL.md`）。

**默认启用策略 `_is_enabled`**（用户没手动设过时怎么算）：
- 用户在 `.skill_state.json` 里显式设过的，以用户为准（禁用集里 → 关，启用集里 → 开）。
- 没设过时看布局：**扁平布局** → 全部默认启用；**分类布局** → 只启用那些顶层分类在“默认启用分类”白名单里的 Skill；分类树里那种直接扔在根目录、没归类的 Skill → 默认关闭（避免它们无谓地撑大注入量）。

**布局判定 `_is_categorized`**：只要发现任何一个 `SKILL.md` 在目录下超过一层深，就判定为分类布局。结果有缓存，安装/卸载改动目录树时缓存失效。

**安装/卸载/查询**：`install`（从 .zip 装，会校验 frontmatter 合法、显式安装默认启用）、`uninstall`、`get_skill`（按名字递归查找）、`enable` / `disable`（改状态并落盘）、`active_skills`（当前启用列表）、`disabled_skills`（当前禁用列表）。

### 2.3 前端入口

- **`/skills` 命令**：打开交互式管理面板，支持 ↑↓ 选择、Enter 看详情、空格启停、d 卸载（需二次确认）、i 安装。启停即时生效（claude-code 下一条消息注入变更通知）；安装/卸载需重启服务才完全生效。
- **只读 Skills / KB 画廊**：JupyterLab 左侧一个只读侧栏，能浏览 Skill 和知识库文档的来源——**翻文档不该依赖 Agent 会话的生命周期**，所以做成独立只读视图。

## 3. 评测与优化 Skill

### 3.1 解决的问题

Skill（尤其知识库 Skill）好不好、加了有没有正收益，不能靠感觉，要有可复跑的评测框架来量化，并驱动优化（比如调注入策略、修检索）。

### 3.2 评测框架（src/eval 目录）

三个核心组件：

- **数据集 `EvalDataset`（文件 loader.py）**：从 JSONL 文件加载题目，支持按 tag 过滤、限制条数。每条含 `id / question / expected（期望答案）/ tags / extra`。
- **异步运行器 `AsyncEvalRunner`（文件 runner.py）**：核心执行器。
  - 用 `asyncio.Semaphore`（信号量）控制并发上限（默认 5），逐题调用传入的 `chat_fn`（对话函数），用 `as_completed` 谁先完成先产出结果。
  - 每题记录：答案、是否通过 `success`、分数 `score`、耗时、错误、可选的过程 trace。
  - `stats` / `report` 汇总：总数、通过数、失败数、错误数、平均耗时、准确率（通过数/已评分数）、平均分。
  - `save` 把每题结果写成 JSONL，并在旁边生成一份 `.report.txt` 报告。
- **评分器 `GraderFn` + `GraderOutput`**：评分函数签名是 `(期望, 答案, 附加) → 评分结果`。默认评分器 `default_grader` 是**大小写不敏感的子串匹配**（期望答案是否出现在回答里）。可通过 `register_grader(名字, 函数)` 注册自定义评分器，在 YAML 配置里用 `grader: <名字>` 引用，也支持 `模块路径:函数` 的导入写法；`grader: none` 表示不评分。

### 3.3 批量执行（YAML 驱动，文件 evaltask.py）

用一个 `tasks.yaml` 描述多个评测任务（每个任务指定数据集、用哪个后端、哪个评分器、并发数、是否采集 trace），`run_tasks` 批量跑，输出每任务的 JSONL + 报告 + 汇总。命令行是 `eval.sh run tasks.yaml`。

### 3.4 这套框架怎么支撑“主动废弃不公平实验”

知识库那次 A/B 之所以能发现“第一版基线虚低是提示词强制拒答造成的”，正是因为评测可复跑、可改单一变量重跑：把“无 Skill 就拒答”的提示词去掉、只留“知识库开/关”这一个变量重新跑一遍，就暴露了问题。**评测框架是“评测驱动优化”的基础设施**，也是重跑当前 Claude 公平 A/B 的现成工具。

> 口径提醒：默认评分器是子串匹配，会漏判“语义等价但表述不同”的答案——所以知识库评测里对自动没过的题做了**人工复核**。答辩时要说清“自动分 + 人工复核”，不要只报自动分。

## 4. 可观测

### 4.1 解决的问题

Agent 到底做了什么、卡在哪一步、花了多少 token——不落数据就没法评测、排障、算成本。

### 4.2 会话事件记录器 SessionEventRecorder（文件 telemetry.py）

- **缓冲式写盘**：事件先在内存里攒着（`record` 只入内存、不做 IO），会话结束时一次性 `flush` 成一个 JSONL 文件，路径是 `.run/sessions/{会话ID}.jsonl`。开销小，不拖慢主流程。
- **健壮性**：写入前先试 `json.dumps` 一下，序列化失败的字段降级成一段错误说明，绝不因为某个对象没法序列化就丢整条记录或抛异常。
- **记录的事件类型**：`session_start/session_end`（会话起止）、`cell_executed`（Cell 执行，含代码/输出/错误/执行序号/耗时）、`agent_prompt`（发给模型的提示）、`agent_response`（模型回复，含工具调用、思考字符数、耗时）、`agent_continue`（用户 /continue yes/no 选择）、`workflow_state`（状态机转换）、`hook_event`（钩子执行结果）。
- **全局单例**：`set_recorder` / `get_recorder` 存取当前记录器，各处代码拿到就能记。

### 4.3 过程追踪 TraceCollector（评测/trace 用）

采集单次交互的结构化过程数据：`thinking`（思考）、`tool_calls`（工具调用）、`usage`（token 用量），整理成一个字典。这就是各后端把异构流统一成 `StreamChunk`（见多 Agent 文档）之后，能被统一采集的原因。

### 4.4 价值

这套数据让“Agent 做了什么、在哪一步、花了多少”可回放。前面文档里的 token 估算、A/B 的耗时/用量、状态转换链路，都来自这里。

## 5. 恢复与复盘

### 5.1 解决的问题

探索性分析会反复改 Cell、改 Notebook；改坏了要能回退，事后要能复盘“当时是怎么一步步做的”。

### 5.2 版本快照（文件 cell_snapshot.py / notebook_snapshot.py）

统一用 `md5(notebook路径)[:12]`（文件 snapshot_utils.py 的 `dir_for` / `notebook_id`）做目录隔离，保证一个 Notebook 始终映射到同一份快照目录。

- **Cell 级快照**：每次 Cell 执行后 `save` 存代码/输出/报错到 `.run/cell_snapshots/<Notebook>/<CellID>/vNNNN.json`；**环形缓冲**保留最近 50 版（超出删最旧）；`list_versions` 按时间倒序列出，`restore` 取回某一版代码。用户可在右键菜单里预览各版本、一键恢复。
- **Notebook 级快照**：`take` 把所有 Cell 的代码/输出/报错存到 `.run/notebook_snapshots/<Notebook>/<时间戳>.json`，保留最近 50 个；`restore` 整体回滚所有 Cell。可通过面板 `/snapshot` 命令手动创建。

### 5.3 会话恢复（文件 conversation_store.py）

前端把每个 Notebook 的对话缓冲存在浏览器 localStorage（快，但只在本机本浏览器）；后端把同一份缓冲**原样镜像**一份到 `.run/conversations/{哈希}.json`。这样重启 JupyterLab、换浏览器、换机器后，会话切换器还能列出并恢复历史对话。后端不解析缓冲内部结构（前端才是格式定义方），只当存储介质，降低耦合。

### 5.4 复盘

复盘靠第 4 节的会话事件 JSONL——一整条“提示 → 模型回复 → 状态转换 → Cell 执行 → 用户确认”的时间线都在里面，可以离线回放整个分析过程。

### 5.5 边界（答辩必答）

- 快照恢复的是 **Cell 的代码和输出文本**，**不恢复内核运行态**（变量、导入的库），也**不撤销数据库写入等外部副作用**。
- 恢复动作本身不再触发新快照。

## 6. QA 速答

- **Q：多 Notebook 隔离能隔离变量吗？** 不能。隔离的是对话历史；同一内核里的 Python 变量仍共享，切换时前端会明确提示。
- **Q：任务跑一半切 Notebook 会乱吗？** 不会。忙时切换被缓存进待切换路径，任务结束回空闲才补切，且只认最后一次。
- **Q：Skill 启用状态存在哪？** 存在 Skill 目录下的 `.skill_state.json`，用户显式操作永远优先于默认策略；分类布局只默认启用白名单分类，避免注入膨胀。
- **Q：评测怎么保证公平/可信？** 单一变量、独立请求、可复跑；默认子串匹配评分器会漏判语义等价，所以对自动没过的题做人工复核，报“自动分+人工复核”。
- **Q：快照能回滚数据库操作吗？** 不能。只恢复 Cell 的代码和输出，外部副作用和内核运行态都不回滚。
- **Q：可观测数据会拖慢主流程吗？** 不会。事件先攒内存、会话结束才一次性落盘，且序列化失败会降级不抛错。
